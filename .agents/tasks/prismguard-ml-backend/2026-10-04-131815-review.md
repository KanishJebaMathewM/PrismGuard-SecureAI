# Per-resource ML models with retrain-on-classify for PrismGuard

This change adds a Python FastAPI backend that trains a separate scikit-learn model for each of PrismGuard's four connected resources (Banking, Government, Company, Research), seeds all four models with labelled prompt data drawn from the existing TypeScript database, and triggers a synchronous model retrain each time an admin classifies a prompt in the review queue. The frontend is wired via a new `src/api.ts` typed fetch client, with `AdminReview.tsx` posting classifications to the backend and `Training.tsx` reading live model accuracy from the database.

Watch for: (1) **confirmed** — `StatsResponse` in `src/api.ts` declares `total_prompts` and `by_resource` but the backend returns `total` and `breakdown` — any code that consumes `fetchStats()` will silently read `undefined`; (2) **confirmed** — `classify_review` always returns `retrained: true` even when `retrain_model` returns `success: False` (not enough samples); (3) **confirmed** — `quickClassify` buttons in `AdminReview` list view update local state only and never hit the backend — admin bulk-classifying via those buttons stores nothing to the DB and triggers no retrain.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The retrain-on-classify flow is structurally correct end to end: the classify route stores the prompt row, calls `retrain_model`, and returns the new version. The gap is that the route always signals `retrained: true` regardless of whether retraining succeeded — so a caller can't distinguish a completed retrain from a skipped one (fewer than 4 samples).

`src/api.ts` compiles cleanly. The `StatsResponse` interface has field-name mismatches with the backend (`total_prompts` vs `total`, `by_resource` vs `breakdown`). TypeScript doesn't surface this because `fetchStats()` is exported but unused; any screen that calls it will silently read `undefined`.

The `AdminReview` list view has "Malicious" and "Safe" quick-action buttons that update local React state only. Only the full `PromptReview` form hits the classify endpoint. A reviewer who bulk-classifies from the list view believes they've fed the model when nothing was stored and no retrain was triggered.

`requirements.txt` pins `scikit-learn==1.5.2` but the models on disk were serialised with 1.7.2 (confirmed by FEAT-001 findings). A clean install of the pinned version will install 1.5.2 and may fail to deserialise the existing `.pkl` files.

<details>
<summary>Issues (4)</summary>

1. **StatsResponse contract mismatch** — `src/api.ts` declares `total_prompts` and `by_resource` but `GET /api/stats` returns `total` and `breakdown`. Fix the interface to match the backend keys, or rename the backend keys to match. Any future use of `fetchStats()` will silently return `undefined` for those fields.

2. **`retrained: true` lie** — `classify_review` in `main.py` hardcodes `"retrained": True` in the response dict regardless of what `retrain_model` returns. If retraining is skipped (fewer than 4 samples), the response still claims it succeeded. Change to `"retrained": retrain_result.get("success", False)`.

3. **Quick-classify buttons don't hit backend** — The "Malicious" and "Safe" buttons in the `AdminReview` list table call `quickClassify(id, status)` which only mutates local React state. These classifications are never stored and never trigger a retrain. Either wire them to `classifyReview` (which requires a `prompt_text` — available on the `item` object) or make it visible in the UI that quick-classify is a local-only label.

4. **`scikit-learn` version pin vs installed** — `requirements.txt` pins `scikit-learn==1.5.2` but FEAT-001 findings note the machine has 1.7.2 installed. The pin and the installed version diverge; when deployed to a clean environment the pinned 1.5.2 will be used, but any `.pkl` files serialised with 1.7.2 will fail to deserialise under 1.5.2 with a version warning or error. Update the pin to match the version the models were actually trained with.

</details>

### StatsResponse field-name mismatch

`GET /api/stats` in `main.py` returns:

```python
return {
    "total": total,
    "malicious": malicious,
    "safe": safe,
    "breakdown": breakdown,
}
```

`src/api.ts` declares:

```typescript
export interface StatsResponse {
  total_prompts: number;   // ← backend key is "total"
  malicious: number;
  safe: number;
  by_resource: Record<string, { total: number; malicious: number }>;  // ← backend key is "breakdown"
}
```

TypeScript doesn't catch this because `fetchStats()` is exported but not consumed by any screen yet. The interface should be `{ total: number; malicious: number; safe: number; breakdown: Record<string, ...> }` — or the backend should be updated to use the snake-case keys to match the interface.

### `retrained: true` regardless of result

```python
retrain_result = retrain_model(resource, db)

return {
    "stored_id": prompt_row.id,
    "resource": resource,
    "retrained": True,          # ← always True
    "new_version": retrain_result.get("version"),   # → None when success=False
    ...
}
```

When `retrain_model` returns `{"success": False, "reason": "not enough samples"}`, `new_version` will be `None` and `version` in the message interpolation will also be `None`. The frontend `ClassifyResponse` interface treats `new_version: string | null` so this won't crash, but the flag is misleading. Fix: `"retrained": retrain_result.get("success", False)`.

### Quick-classify list buttons

`AdminReview.quickClassify` updates `items` state to reflect a new status in the table row but makes no API call:

```typescript
function quickClassify(id: string, status: ReviewStatus) {
  setItems((prev) => prev.map((item) => (item.id === id ? { ...item, status } : item)));
}
```

The `item.prompt` and `item.resource` are available on the `ReviewItem` object, so wiring this to `classifyReview` is straightforward. The current behaviour means a reviewer who bulk-classifies from the list view believes they've fed the model when nothing was recorded.

### scikit-learn pin mismatch

`requirements.txt` pins `scikit-learn==1.5.2`. FEAT-001 findings state the dev machine has 1.7.2 installed. The `.pkl` files on disk were serialised by 1.7.2. scikit-learn does not guarantee cross-version deserialisation compatibility for Pipeline objects — a fresh `pip install -r requirements.txt` in a clean environment will install 1.5.2 and may fail to load the models. The pin should be updated to `scikit-learn==1.7.2` to match the environment in which the models were trained.
