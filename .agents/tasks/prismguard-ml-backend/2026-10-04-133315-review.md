# Per-resource ML backend with retrain-on-classify for PrismGuard

The change adds a complete Python FastAPI + scikit-learn backend under `backend/` that trains an independent TF-IDF + LogisticRegression pipeline for each of the four resources (Banking, Government, Company, Research), stores every classified prompt in SQLite, and retrains the relevant model synchronously whenever an admin classifies a prompt. The frontend is wired via a new `src/api.ts` typed fetch client; `AdminReview.tsx` now POSTs classifications to the backend, and `Training.tsx` pulls live model stats from `GET /api/models`.

Watch for: (confirmed) the classify route response includes an undeclared `accuracy` field not present in the TypeScript `ClassifyResponse` interface — harmless at runtime but the contract is slightly looser than the type implies; (confirmed) `detection_accuracy` is reported as 100% for all resources except Research after seed, which reflects overfitting on the small synthetic test split rather than genuine generalisation ability; (likely) no deduplication guard on the classify route means repeated admin submissions of the same prompt text will create duplicate rows that inflate training sample counts without adding information.

**Verdict**: APPROVED

---

## High-level view

One scikit-learn pipeline per resource is stored as a `.pkl` file in `backend/models/` and lazy-loaded into a module-level cache on first use. The seed script populates ~40 balanced samples per resource (from `researchPrompts.ts` plus synthetic prompts) and runs an initial `retrain_model` for all four resources before the server starts. All four model files are present on disk.

The retrain-on-classify flow is implemented end-to-end and confirmed working: `POST /api/admin/reviews/{id}/classify` inserts the prompt row with `source='admin'`, immediately calls `retrain_model(resource, session)` synchronously, bumps the version minor counter, and returns `retrained: true` with the new version string. The DB confirms admin prompts land in the `prompts` table and model version increments correctly.

The TypeScript frontend is fully wired. `classifyReview` is called from both the `PromptReview.handleSubmit` async path and the quick-classify path in the list view — the quick-classify path calls it fire-and-forget with a `.catch` guard. `Training.tsx` fetches live stats on mount with a static fallback, and `vite.config.ts` proxies `/api` to `:8000`. TypeScript typecheck exits 0.

The `ClassifyResponse` TypeScript interface is missing the `accuracy` field that the backend returns alongside the other fields. This is an undeclared contract extension — the frontend doesn't consume `accuracy` so there's no runtime breakage, but the type doesn't reflect the actual wire shape. A single field addition to `ClassifyResponse` closes this.

Seed data accuracy reads 100% for Banking, Government, and Company after initial training. With 40 samples and `test_size=0.2`, the test split is 8 rows of highly distinctive synthetic text. TF-IDF on short, domain-specific attack phrases memorises the test set easily at this scale. The `class_weight='balanced'` setting is correct but doesn't prevent overfitting at this sample count. The reported accuracy is not meaningful for assessing real-world performance; it will stabilise as admin-classified real prompts accumulate.

<summary>Issues (2)</summary>

1. **Undeclared `accuracy` field in ClassifyResponse** — `POST /api/admin/reviews/{id}/classify` returns `{ stored_id, resource, retrained, new_version, accuracy, message }` but `ClassifyResponse` in `src/api.ts` only declares `{ stored_id, resource, retrained, new_version, message }`. The frontend ignores the field so there's no runtime error, but the type contract is incomplete. Add `accuracy: number | null` to `ClassifyResponse`.

2. **No deduplication on admin classify** — The classify route creates a new `Prompt` row unconditionally, with no check for an existing row with the same `text` and `resource`. Repeated admin submissions of the same prompt inflate `training_samples` in `model_metadata` without adding new information to the model. Mirror the idempotency guard from `seed_data.py`: check for an existing row by `text` + `resource` before inserting.

### Retrain-on-classify flow

The end-to-end path is: `AdminReview.tsx` → `classifyReview(id, payload)` → `POST /api/admin/reviews/{id}/classify` → insert `Prompt` row with `source='admin'` → `retrain_model(resource, db)` → `joblib.dump` updated `.pkl` → bump `ModelMetadata.version` minor → `session.commit()` → return `ClassifyResponse`. The `review_id` path parameter is accepted as a string but never looked up — the backend uses the body payload exclusively, which matches the plan's intent (the frontend still reads `reviewQueue` from static data).

One subtle issue: the classify route returns `accuracy` in its response dict but `ClassifyResponse` in `src/api.ts` doesn't declare it. At runtime `res.json() as Promise<T>` does no shape validation so the extra field is silently ignored, but callers who destructure the response won't see it, and future consumers of the type will be surprised.

### Seed coverage and class balance

All four resources have seed data:

- Research: 32 malicious (from `researchPrompts.ts`, verbatim) + 20 safe = 52 rows
- Banking: 20 malicious + 20 safe + admin-classified additions = 44 rows (as of review)
- Government: 20 malicious + 20 safe = 40 rows
- Company: 20 malicious + 20 safe = 40 rows

Class balance is approximately 50/50 for all resources, appropriate for `class_weight='balanced'` and avoiding the one-class fallback path in `retrain_model`. The `has_both_classes and len(rows) >= 10` branch is exercised for every resource.

### Model accuracy and overfitting

The 100% test accuracy on Banking/Government/Company seed data isn't a code defect — it's the expected outcome of fitting a TF-IDF bigram model on short, highly stereotyped synthetic phrases with an 8-row test set. The `detection_accuracy` column in `model_metadata` is intended as a production signal; at seed scale it's a warm-up placeholder. Research's 90.9% is more representative because the 32 research prompts are drawn from real attack examples (the original `researchPrompts.ts`) that share vocabulary with the safe prompts.

### Admin classify deduplication gap

`seed_data.py` uses an existence check before inserting:
```python
existing = session.query(Prompt).filter_by(text=item["text"]).first()
if not existing:
    session.add(Prompt(**p))
```
`main.py`'s classify route does not. Two clicks on Submit for the same review will insert two identical rows, the second retrain will report one more sample than actual unique inputs, and the model gets no new signal. The version counter also increments spuriously. This is the only parity gap between seed and classify behaviour.

### Not tested

There are no automated tests in the repository — no pytest files for the backend routes or ML functions, and no Vitest/Jest tests for `src/api.ts` or the updated components. The absence is noted; the task specification did not require a test suite, and the manual verification checklist in `FEAT-001.json`/`FEAT-002.json` was used instead. Adding at minimum a pytest smoke test for `retrain_model` and `predict` would protect against regressions when sklearn or numpy versions change.
